Scope and terminology

A workflow defines steps and outcome routes. An execution is one run for a project and input. A step invokes a package or waits for a decision. An optional stage groups agent steps and defines a bounded loop and human decision boundary. Multiple executions can progress independently within one local service.

01 / System architecture

Component responsibilities and interfaces

The control plane depends on execution.Engine. The scheduling adapter depends on execution.Runner for package invocation. The application composition root connects these implementations; controller and runner packages do not import Hatchet.

02 / Workflow definition

Workflow configuration

A project’s factory.json references agent packages and declares named steps, outcome routes, and stage policy. Packages own their runner configuration, tools, skills, and model integration.

01

Outcome routing

The agent submits an outcome. Its configured on map determines the next step. The controller does not infer success from prose.

02

Loop execution

Sequential mode follows step routes. Concurrent mode starts all loop members together and reduces their results at a round barrier.

03

Human decision policy

A stage can require a named human decision before leaving its loop. Reaching the loop limit escalates to that decision; without a required human decision, the execution fails.

03 / Communication contract

Messaging and result acceptance

Active agents communicate through execution-scoped MCP threads. Progress, publications, questions, and results share a message envelope using A2A content parts. A runner adapter connects that protocol to the agent’s native interface.

Each concurrent member submits its own result. The round advances only after all required results are accepted; peer messages alone cannot advance the workflow.

Runner integration requires an adapter. The bundled Pi adapter translates native events and steering input. Other runners must implement the same communication and result contract.

04 / Operational interface

CLI and terminal monitor

The CLI exposes execution creation, inspection, messaging, decisions, retry, and cancellation. The monitor uses the same service operations. An external agent can invoke the CLI with the operator skill. Examples use the current factory binary and factory.json format.

05 / Engineering status

Implementation status and limitations

The current implementation targets a trusted, single-user host. It runs a local control service, PostgreSQL, a self-hosted Hatchet engine, and supervised agent processes.

The engine and runner interfaces provide replacement points. Distributed deployment, authenticated decision authority, and enforceable workload isolation remain incomplete.

AVAILABLE

Local end-to-end execution

Configured agents, routes, bounded loops, concurrent sessions, human decisions, CLI operations, and terminal monitoring.

AVAILABLE

Persistent operational records

PostgreSQL execution, session, decision, and event records. Hatchet owns durable scheduling behind the engine interface.

BOUNDARY

Host processes are not sandboxes

The local runner inherits the user’s permissions. Enforced filesystem, network, and secret isolation requires a future isolated runner.

FUTURE

Distributed operational guarantees

Multi-worker leases and session routing, authenticated authority, crash reconciliation, and engine/projection atomicity remain work to complete.
