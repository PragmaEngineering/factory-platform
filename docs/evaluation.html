01 / The assignment

Task and acceptance criteria

The baseline service already supported task creation and lookup. The change had to preserve existing behavior while adding byte-exact replay and concurrency guarantees, without new dependencies.

Required behavior

201 / replaySame key + exact body returns the original response.
409 / conflictSame key + different bytes must not create a task.
400 / blank keyHeader absence differs from an explicitly blank header.
Concurrent safetyExactly one task for simultaneous matching requests.

Invalid requests must not reserve a key. Storage remains in memory for one handler’s lifetime. Existing endpoints, response shapes, and sequential IDs remain intact. Read the original brief ↗

F-001 / DESIGN REVIEWRESOLVED IN REV 2

Absent header ≠ blank header

The first plan risked treating a missing Idempotency-Key like an explicitly empty value. That would break the required legacy create path.

OBSERVED CORRECTIONThe revised plan uses header-map presence separately from value trimming, preserving the three-way distinction.

F-002 / DESIGN REVIEWRESOLVED IN REV 2

Buffering must preserve strict decoding

The proposed switch to json.Unmarshal risked dropping existing unknown-field rejection while adding raw-body comparison.

OBSERVED CORRECTIONThe revised plan buffers bytes but retains json.Decoder with DisallowUnknownFields.

The architecture review tracked four findings in total. The other two clarified blank-key error wording and the exact 409 response body. These are concrete review contributions, not a measured defect-prevention rate.

05 / Remaining engineering work

Observed problems and proposed follow-up

The agents continued after six tool errors without a workflow retry. Additional concerns include unenforced access boundaries, masked command failures, reviewer mutations, and report accuracy. These observations are independent of the final execution state.

01

Invalid publication payload

The architect’s initial publication omitted the required structured data part. The server rejected it and the agent repaired the call.Next: make kind-specific payload requirements easier to satisfy before submission.

02

Reads before publication

Reviewers attempted three reads before their expected artifacts existed. Two additional architecture-review tool errors came from help-command invocations.Next: use explicit publication readiness rather than racing project-file creation.

03

Unenforced workspace scope

The builder searched runtime and registry locations for a helper, used generic temporary filenames, and attempted a Go tool invocation with errors suppressed.Next: enforce workspace and network access at the runner boundary; prompts are not isolation.

04

Masked command failures

Shell pipelines, suppressed output, and || true can conceal failing checks. The reviewer ran plain test, race, and vet commands, but this does not solve the general evidence problem.Next: record individual command outcomes without masking failures.

05

Reviewer mutation and report accuracy

The reviewer ran go mod tidy, which can mutate module files. Its report also mislabeled vet as lint and described t.Helper as a testify pattern.Next: separate read-only verification, observed commands, and derived conclusions.

06

Planning proportionality

Spec and plan together contain 2,107 body words. The shared renderer helped presentation overhead, but proportionality to this task remains unproven.Next: compare document relevance and workflow cost across task sizes.
